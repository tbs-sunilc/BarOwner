Codex answer / suggestion:

No, those exact suggested bar-owner APIs are currently NOT available in this project.

These APIs are NOT found:

GET /api/v1/bars/{barId}/wallet-purchases
GET /api/v1/bars/{barId}/wallet-purchases/{paymentId}
GET /api/v1/bars/{barId}/wallets/{walletId}

What is available right now:

1. Dashboard summary API:
GET /api/v1/bars/{barId}/dashboard

This API returns only the dashboard payload. For Recent Wallet Purchases it returns last 10 captured wallet purchase payments only.
It gives fields like paymentId, purpose, amountInPaise, paymentMethod, status, capturedAtUtc.
It does NOT give proper customer name, walletId, bottle details, volume, remaining wallet balance, or full transaction ledger.

2. Revenue API:
GET /api/v1/bars/{barId}/revenue

This API is for revenue analytics and GST summary. It is not a full wallet-purchase list API.

3. Customer wallet detail API:
GET /api/v1/wallets/{id}

This API exists, but it is customer/user scoped. It uses the logged-in user id, so it is not suitable for bar-owner row View button unless backend adds owner-safe access.

My suggestion:

For dashboard "View All", create a proper bar-owner wallet purchases list API later:
GET /api/v1/bars/{barId}/wallet-purchases

For row "View", create a detail API later:
GET /api/v1/bars/{barId}/wallet-purchases/{paymentId}

That detail API should return payment + customer + wallet + bottle + transaction information, so the owner can open a modal or detail page.

Until those APIs are created, the current row View button should either be hidden/disabled or replaced with a clear future action. Current View All going to /revenue is also misleading because /revenue is analytics, not all wallet purchases.


Implementation decision:

We chose the recommended path.

Backend APIs to add/use:
GET /api/v1/bars/{barId}/wallet-purchases
GET /api/v1/bars/{barId}/wallet-purchases/{paymentId}

Frontend behavior:
Dashboard View All should go to /wallet-purchases.
Dashboard row View should go to /wallet-purchases/{paymentId}.

Reason:
This keeps /revenue as analytics only and makes wallet purchases a proper owner workflow with list + detail.
